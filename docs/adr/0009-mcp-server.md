# ADR-0009: An MCP server for AI agents, on the API server

Status: proposed (2026-11-16).

## Context

People use AI agents (Claude Code, Cursor, IDE assistants, their own agents) to investigate incidents and write code.
The agents can query an observability backend through the Model Context Protocol (MCP): the agent's client connects
to a remote MCP server, lists its tools and calls them as the model decides. Commercial observability products offer
such a server; users expect to point their agent at their ObserveCraft instance the same way, with a URL and a key.

Assist (`assist/tools.rs`) already gives a model tools over the org's data: it calls the UI's own handlers as the
signed-in user, so the org, the user's role and their log restrictions apply. An MCP server needs the same thing, with
the model on the other side of an HTTP connection.

The MCP specification changed shape in revision 2026-07-28: requests carry their protocol version and client
information in `_meta` (mirrored into `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers), there is no
`initialize` handshake and no session, and `server/discover` lists the supported versions. Clients released before
it (2025-03-26 to 2025-11-25) still open with `initialize`, and most agents in use today are such clients.

## Decision

**Transport.** Streamable HTTP at `POST /api/v1/mcp` on the API server (`observecraft-server`), next to the API it
reuses. Every request is answered with one JSON object (`application/json`); there are no SSE streams, no session ids
and no server-initiated requests, so any replica answers any request. `GET` and `DELETE` answer 405. Notifications
answer 202. A request whose `Origin` header is present and is neither the public URL nor an allowed CORS origin is
refused with 403 (DNS rebinding).

**Protocol versions.** The server is dual-era: `2026-07-28`, and the legacy `2025-11-25`, `2025-06-18` and
`2025-03-26`. A request with `_meta["io.modelcontextprotocol/protocolVersion"]` is served statelessly by the 2026 rules
(headers must match the body, else 400 `HeaderMismatch` -32020; unknown versions get 400 -32022 listing the supported
ones; unknown methods 404 -32601). `initialize` selects the legacy rules: the server answers with the client's version
when it supports it, else with `2025-11-25`; later legacy requests send `MCP-Protocol-Version` (absent means
`2025-03-26`). Since nothing is kept between requests, legacy clients need no session either. Methods: `initialize`,
`server/discover`, `ping`, `tools/list`, `tools/call`; notifications are accepted and ignored.

**Hand-written, no SDK.** The official Rust SDK (`rmcp`, Apache-2.0, axum 0.8) would pass `cargo deny`, but it does
not fit cleanly: its HTTP transport is its own tower service with session handling, so our key authentication, error
shapes and audit would sit in adapters around it; its tool routing is built for typed handlers generated by macros,
while our tools are data (name, JSON Schema, a call into an existing handler) as Assist's are; and it adds a fast-moving
dependency (three major versions in a year) for what is five methods of JSON-RPC over one POST route. The protocol is
in `mcp/mod.rs` (parsing, version and header checks, dispatch over a `Toolbox` trait, unit-tested without a database),
the tools in `mcp/tools.rs`, the route in `routes/mcp.rs`.

**Authentication and tenancy.** An application key, as the management API takes it (ADR-0003): `Authorization:
Bearer ocak_…`, or `DD-APPLICATION-KEY` (with an optional `DD-API-KEY` ingest key, which must belong to the same
org). Session cookies are not accepted, so the route has no CSRF surface. Without a valid key the answer is 401 with
`WWW-Authenticate: Bearer`. The route is merged outside the session middleware, as the Datadog-compatible routes are,
and resolves the key with the same code (`datadog_api::resolve`). The org and the user come only from the key; tool
arguments never name an org. Each tool calls the UI's handler with that org (`OrgId`), so telemetry goes through
`AppState::ch(org)` and its per-org limits, and logs through the user's restriction queries (`log_access::for_user`).

**Read-only tools in v1.** The tools only read. They are calls of the existing handlers, the same ones the UI, Assist
and the Datadog-compatible routes use; there is no new SQL and no new data model:

| Tool | Handler |
|---|---|
| `search_logs`, `aggregate_logs` | `logs::search`, `log_analytics::aggregate` |
| `query_metrics`, `search_metrics` | `metrics::timeseries`, `metrics::catalog` |
| `search_spans`, `get_trace`, `list_services` | `apm::search_traces`, `apm::trace`, `apm::services` |
| `search_monitors`, `get_monitor` | `monitors::search`, `monitors::get_one` |
| `search_incidents`, `get_incident` | `incidents::search`, `incidents::get_one` |
| `search_events` | `events::search` |
| `search_hosts`, `search_kubernetes` | `hosts::search`, `kubernetes::search` |
| `search_dashboards`, `get_dashboard` | `dashboards::search`, `dashboards::load` (without recording a view) |
| `search_error_issues` | `error_tracking::search_issues` |
| `search_security_signals`, `get_security_signal` | `security_signals::search`, `security_signals::get` |
| `search_vulnerabilities` | `cloud_security::infra_vulnerabilities` |
| `search_code_security_findings` | `code_security::list_findings` |

Tools Assist has too reuse Assist's calls (`OrgTools::call`). Every tool is annotated `readOnlyHint`.

**Output limits.** Results are compact JSON after a one-line summary, as Assist's are. Row caps per tool (logs 100,
spans and events 50, …, defaults about 20), log messages cut at 500 characters and attribute values at 200, at most 40
metric series with at most 120 points each, at most 200 spans of a trace. A time range may cover at most 31 days. A
result longer than 50 000 characters is cut, with a note saying so and how to narrow the call. Invalid arguments and
handler errors come back as tool results with `isError: true`, so the model can correct itself; only malformed
requests and unknown tools are JSON-RPC errors.

**Timeouts and rate.** A tool call is abandoned after 30 seconds (the ClickHouse queries under it also carry the org's
`max_execution_time`). Each replica allows a user 50 tool calls in 10 seconds; more get a tool error asking to retry.
The org's query concurrency limit (`org_limits.rs`) bounds the load across users.

**Audit.** Every tool call is written to the org's audit trail (`mcp.tool_call`, the tool as target, the arguments
cut at 500 characters), as the acting user, and logged with its duration and outcome.

## Out of scope (later)

- Write tools (create a monitor, declare an incident, mute): they need per-org switches and confirmation semantics.
- OAuth 2.1 sign-in for MCP clients through the instance's OIDC login and protected resource metadata, so users don't
  paste keys.
- Toolset selection by URL parameter, a `max_tokens` argument, SSE progress notifications, resources and prompts.
- Tools whose internals don't exist yet as one call: SLO status, RUM sessions, CI pipelines, profiles, synthetics.
